# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An automated stock trading bot for the Korea Investment & Securities (한국투자증권, KIS) Open API.

The repo is mid-migration from a **browser-driven** architecture (React SPA polls KIS directly and runs the trading state machine client-side) to a **server-driven** one (`apps/trading-server` runs cron-scheduled auto-trading unattended; the browser app becomes a thin control/monitor surface). Both halves currently coexist:

- **Legacy (still running, unmodified during the migration)**: React SPA (`apps/stock-trading-bot`) + `apps/kis-server` proxy. Watches trading-volume-ranked stocks, auto-buys based on configurable criteria, auto-sells at configured profit/loss percentages — all client-side, only while the browser tab is open.
- **New (active development)**: `apps/trading-server` — see "Server-side auto-trading" below. Owns KIS credentials itself, runs 4 independent entry strategies + a shared trailing-stop exit, exposes a REST API, and sends Discord notifications. `apps/trading-control` is the REST client for it (see "Control frontend" below).

## Repo layout

Nx monorepo (npm workspaces, Nx 17), one `tsconfig.base.json` with path aliases:

- `apps/stock-trading-bot` — the React 18 SPA (Vite, styled-components, Recoil). Entry: `src/main.tsx` → `src/app/app.tsx`. **Legacy** — calls KIS directly from the browser via `apps/kis-server`.
- `apps/kis-server` — Express proxy (`src/main.mjs`) that forwards `/api-proxy/*` to `openapi.koreainvestment.com:9443`, injecting `appkey`/`appsecret`/`authorization` headers from whatever the browser sends. Exists solely to get around KIS API host/CORS restrictions from the browser. Kept running as-is for the legacy FE; `apps/trading-server` does **not** go through it (see below).
- `apps/trading-server` — Express + Prisma/Postgres app that owns KIS credentials and runs auto-trading unattended on a cron schedule. See "Server-side auto-trading" below.
- `apps/trading-control` — React 18 SPA (Vite, styled-components) that's the REST client for `apps/trading-server`, meant to be loaded in an Android WebView. See "Control frontend" below.
- `services/trading` (`@services/trading`) — legacy FE trading feature: pages (`Main`, `AdvanceOrder`, `LogCenter`), hooks, and the `SellByPercent` trading strategy. Not used by `trading-server` (that app has its own parallel, DB-backed reimplementation under `apps/trading-server/src/trading/`).
- `shared/apis/kis` (`@shared/apis/kis`) — legacy FE's KIS REST API client (axios + browser-localStorage token cache). `trading-server` does **not** import this (browser-only globals); it has its own client under `apps/trading-server/src/kis/`.
- `shared/states/global` (`@shared/states/global`) — Recoil atoms and the `TradingStrategy` abstract class; app config and order-list state, persisted via `local-store`.
- `shared/hooks/api-hook` / `shared/hooks/util-hook` — `useKisApi` (fetch+cache+session-retry wrapper around KIS API functions) and small utility hooks (`useStateRef`, rerender).
- `shared/ui/design-system-v1` — shared styled-components UI kit (layout primitives, buttons, toast, routing components).
- `shared/utils/date`, `shared/utils/localstorage` — small standalone utilities (`ObjectBasedLocalStore`, `ListBasedLocalStore`).

Path aliases (see `tsconfig.base.json`) map each `shared/*`/`services/*` library to its `src/index.ts` barrel — always import from the alias (e.g. `@shared/apis/kis`), not by relative path across project boundaries. `apps/trading-server` is a standalone Express app and doesn't use these aliases (plain relative imports within `apps/trading-server/src/`).

## Legacy architecture / data flow (apps/stock-trading-bot, browser-driven)

1. **`CheckBalance`** (`shared/apis/kis/src/run-process/check-balance.ts`) is a singleton poller: once it has listeners, it calls `InquireBalance` on a 1s `setTimeout` loop and fan-outs the result to all registered listeners. Started/stopped once in `App` via `CheckBalance.run()` / `.destroy()`.
2. **`TradingStrategy`** (`shared/states/global/src/order/abstract/trading-strategy.ts`) is an abstract state machine (`checking → watching-for-sell → sell-waiting → done|error`) per stock code. `SellByPercent` (`services/trading/src/trading-strategy/sell-by-percent.ts`) is the concrete strategy: it registers `CheckBalance` listeners at each state to react to balance/price changes, places market sell orders via `OrderCache` when a high/low % target is hit, and calls `removeOrderToday()` when done.
3. **`useKisApi`** (`shared/hooks/api-hook`) wraps a KIS API function with React state, an in-memory response cache keyed by `JSON.stringify(request)`, and automatic retry (up to 5x) when the API responds with a `nosession` code (stale token).
4. **Recoil state** (`shared/states/global`) holds `OrderDate`/`OrderStocks`/`OrderTrading` (today's order list, persisted to localStorage via `OrderListStore`) and `AppConfig` (trading parameters: refresh rate, working hours, buy/sell %, order amount limits — persisted via `ObjectBasedLocalStore`).
5. **Token handling**: `axios-instance.ts` reads a cached token from `window.localStorage['kis-token']`, refreshes it via `oauth2/tokenP` when missing or when the API returns a session-expired error code (`EGW00121`/`EGW00123`), and rebuilds the axios instance with the new token.
6. All KIS request bodies/headers use the API's native field names (e.g. `PDNO`, `ORD_QTY`, `tr_id`) — these correspond 1:1 to KIS Open API documentation, not internal conventions.

## Server-side auto-trading (apps/trading-server)

Express + Prisma/Postgres app, structurally independent from the rest of the monorepo (no `@shared/*` imports — see Repo layout above). Calls `openapi.koreainvestment.com:9443` (real) / `openapivts.koreainvestment.com:29443` (paper) directly; does not go through `apps/kis-server`.

**KIS client** (`apps/trading-server/src/kis/`): `env.ts` resolves `KIS_ENV` (`paper` default | `real`) to the matching `KIS_REAL_*`/`KIS_PAPER_*` env vars, or takes an explicit override; `tr-id.ts` maps buy/sell/balance tr_id per env (`V`-prefix paper vs `T`-prefix real — paper also uses the plain `inquire-balance` endpoint instead of `inquire-balance-rlz-pl`, since realized-P&L isn't available on paper accounts). `client.ts` owns access tokens itself (persisted in the `kis_tokens` table, not browser localStorage), cached **per env** (`Map<KisEnvName, ...>`) rather than a single instance — `fetchBusinessDay` (chk-holiday) is hardcoded to always call with `real` credentials regardless of the active `KIS_ENV`, because that tr_id isn't available on paper accounts at all (confirmed by hitting it live — `EGW02006 모의투자 TR 이 아닙니다`), so a `paper`-mode process still needs a live `real` client alongside its `paper` one. Every request from `getKisClient()`'s axios instance is paced through `request-queue.ts` (env별 최소 요청 간격 강제, `KIS_RATE_LIMIT_REAL_MS`/`KIS_RATE_LIMIT_PAPER_MS`로 override) to stay under KIS's official REST rate limit (API Portal 공지, 2026-04-20 기준: 실전 초당 18건 / 모의 초당 1건, 계좌 단위) — a still-rejected `EGW00201`/`EGW00215` response is retried a few times with backoff as a last resort — since 2026-08-05, the same retry (`retryRequest()`, shared budget) also covers pure network-level failures with no HTTP response at all (`ECONNRESET`/`ECONNABORTED`/`ETIMEDOUT`/`EPIPE`, e.g. "socket hang up") — the original interceptor only checked `error.response`, which doesn't exist for these, so they used to fail immediately with zero retry even though they're very likely the same KIS-side-load root cause as the rt_cd-based rate limit codes. `quotations.ts` wraps the KIS ranking/status endpoints — see Strategies below for which one feeds which.

**Known gotcha (2026-08-03 incident, multi-part)**: a burst of ~13 VI-triggered buys right at market open, on top of the 1s `BalancePoller` loop, tripped KIS's paper-account rate limit on one sell order. `placeMarketOrder` had no try/catch, the exception became an unhandled promise rejection (the `BalancePoller` listener that threw is async — `tick()`'s `try/catch` only catches *synchronous* throws from a listener call, not rejections from its returned promise), and with no `process.on('unhandledRejection'/'uncaughtException')` handler anywhere the whole process died with zero trace (no DB row, no Discord message) — leaving every open position frozen mid-state for hours. First fix: the rate-limit queue above, wrapping every `placeMarketOrder` call site (`position-watcher.ts`'s `watchForSell`/`forceSell`, `execute-buy.ts`) in try/catch → `fail()`/`buy_failed`, and a `process.on(...)` safety net in `main.ts`.

That safety net immediately exposed two deeper bugs on the very same day. (1) KIS returns most business errors — including rate-limit rejections — as **HTTP 200 with `rt_cd:'1'` in the body**, not an HTTP-level error, so the original retry logic (hung off axios's error/reject handler) never actually fired, and the specific code that hit was `EGW00215` anyway, not the `EGW00201` that was handled. Worse, `inquireBalance()` read `res.data.output1` without checking `rt_cd` first, so a rate-limited call silently became "0 holdings" — fanned out via `BalancePoller` to every listener at once, causing every open position to be mistaken for a manual sell in the same tick. Fixed by `kis/client.ts`'s `assertKisSuccess()` (checked in `inquireBalance()` and every `quotations.ts` fetcher) plus a **success-branch** interceptor check for rate-limit codes (`EGW00201`/`EGW00215`), since the error-branch one alone never triggers for this class of failure. (2) Separately, a transient DB hiccup right at boot (`P1001`, Prisma pool not yet warm) made `resumeTodaySessionIfNeeded()` throw *before* `startTradingCron()` ran in `main.ts` — the unhandled-rejection net kept the process alive, but the 09:00/15:25/16:00 cron schedule was simply never registered for that process's entire lifetime, so that day's forced-liquidation and session-close silently never fired even though trading itself kept working fine. Fixed by wrapping the *entire* boot sequence (`BalancePoller.run()` → DB-readiness check with retry, up to 30s → `resumeTodaySessionIfNeeded()` → `startTradingCron()`) in one try/catch in `main.ts`: any failure sends a Discord alert and calls `process.exit(1)` rather than continuing in a half-initialized state — deliberate, since Jenkins reports deploy success purely from the container starting, so this is the only point that can surface an app-level boot failure. Also surfaced in the same incident: `lib/date.ts`'s day/time helpers used to derive "today"/"now" from the process's local system-TZ getters with no `TZ` pinned anywhere in the Dockerfile/Jenkins deploy command — it happened to line up with KST that day, but isn't guaranteed, so it's now computed explicitly via `Intl.DateTimeFormat({ timeZone: 'Asia/Seoul' })` regardless of the host's actual system TZ.

**Known gotcha (2026-08-04 incident)**: KIS's `inquire-balance` caps a single call at **20 rows on paper / 50 on real** (documented in KIS's own reference script, `inquire_balance.py` — not in the prose docs) and requires following a continuation protocol (response header `tr_cont` = `M`/`F` means more pages exist; echo the response body's `ctx_area_fk100`/`ctx_area_nk100` back as `CTX_AREA_FK100`/`CTX_AREA_NK100` with request header `tr_cont: 'N'` to fetch the next page) — `inquireBalance()` never did this, it just read page 1 and returned. As VI-momentum buying accumulated concurrent paper positions past 20 that day, every position pushed off page 1 became invisible to every caller of `inquireBalance()` (`BalancePoller`, `PositionWatcher.checking()`/`watchForSell()`, `forceSell()`) — bought positions sat stuck in `checking` state all day (never detected as held), the 15:25 forced-liquidation sweep couldn't see them either (its own fresh `inquireBalance()` call had the same blind spot), and 134 positions were left open in the paper KIS account at market close while the DB showed every position as `done`. The initial hypothesis was rate-limit queue congestion or the 15:20–15:30 closing-auction window being too tight — both ruled out by checking the actual event timestamps in the DB (the 15:25 sweep's real sells all completed within 16 seconds, no congestion). Fixed by making `inquireBalance()` (`kis/trading.ts`) loop through pages (capped at 10, matching the reference script's own `max_depth`) until the response `tr_cont` header stops being `M`/`F`.

**Cron schedule** (`src/cron/schedule.ts` + `session.ts`, `node-cron`, `Asia/Seoul`, weekdays only): `09:00` first runs `liquidateStalePositions()` — sells everything currently in the KIS balance at market price before doing anything else that day. The account is dedicated to this bot, so whatever's in balance is assumed to be a leftover position that a previous session failed to close (the 134-stray-positions incident above, but also a general safety net for any future `done`-marking bug) — DB matching isn't required to decide *whether* to sell. For each code sold, it looks up the most recent `PositionWatcher` for that code (no `state` filter — even one already, incorrectly, marked `done` gets overwritten with the real result) and logs the correction event under the **original** `Order`'s `sessionId`, not today's, so a later monthly rollup sees accurate numbers even though that day's report already went out; any DB row still open with nothing left in the live balance (already gone via some other path) is reconciled straight to `done` with no sell needed. `TradingSession.startingCash` for the day is then set to `availableCash + Σ(price × qty)` of everything just sold, since the sell orders haven't settled yet at that point and the live `prvs_rcdl_excc_amt` wouldn't reflect them — then opens today's `trading_sessions` row (checks business day via KIS, starts all 4 strategy scanners + the foreign-institution cache) → `15:15` (moved up from `15:25` the same day — a 5-minute buffer wasn't enough to force-sell 100+ positions before the 15:20–15:30 closing auction) stops new-order scanning and force-sells (`PositionWatcher.forceSell`) every still-open position ahead of the `15:30` market close → `15:30` (moved up from `16:00` — no reason to wait 30 more minutes after close) marks the session closed **and now also calls `PositionWatcher.stopWatching()` on every still-unresolved position** (detaches its `BalancePoller` listener without touching its DB `state`) so the next day's `liquidateStalePositions()` can reconcile it from the live balance. Until 2026-08-05 this was "`BalancePoller`/unfinished watchers are left running regardless — the exit side doesn't stop on a clock" — but a position stuck in `sell_waiting` (e.g. a partial-fill leftover) kept its listener alive indefinitely, so `BalancePoller` kept polling `inquireBalance()` every second all evening long, including into a KIS after-hours maintenance window that was rejecting calls with "모의투자 서비스가 지연되고 있습니다." On boot, `resumeTodaySessionIfNeeded()` re-attaches in-memory watchers/scanners if the process restarted mid-session (crash/redeploy) — it already skips this when `closedAt` is set, so it doesn't fight with the new stop-on-close behavior.

**Entry strategies** (`src/trading/*-scanner.ts`), all independently toggleable via `TradingConfig` and all funneling into the same `executeBuy()` (`execute-buy.ts`) → same `PositionWatcher` exit:
- `scanner.ts` — 거래대금순위 (KIS `volume-rank`, `FID_BLNG_CLS_CODE=3`), optionally required to also appear in `foreign-institution-cache.ts`'s 5-min-refreshed 외국인/기관 순매수 상위 list (`requireForeignInstitutionNetBuy`). `FID_INPUT_ISCD` hardcoded to `0001`(코스피 업종코드) instead of `0000`(전체) since 2026-08-07 — see the KOSPI-only note below.
- `vi-scanner.ts` — VI(변동성완화장치) release momentum: KIS `inquire-vi-status`, buys codes released within the last `RECENT_RELEASE_WINDOW_SEC` (90s, tightened from 180s on 2026-08-05 as a strategy experiment — this is a freshness filter on the release event itself, not a "watch N seconds of price action" window: the buy is a market order placed on the very tick the release is first seen, so a shorter window just refuses to chase releases we noticed too late). Ticks every `SCAN_INTERVAL_MS` (3s, tightened from 5s the same day) — note every KIS call from every scanner/BalancePoller funnels through the one shared per-env `request-queue.ts`, so a shorter tick interval mostly means joining that queue sooner, not a guaranteed faster check (`viStrategyEnabled`). Applies no price/volume filter at all — unlike `scanner.ts`/`gap-scanner.ts`, `minTargetAmt`/`maxCandidatePrice`/`minTradingCount` don't affect this strategy. `fetchViStatus()`'s `FID_RANK_SORT_CLS_CODE` changed from `0`(전체) to `1`(정적만) on 2026-08-07: 정적 VI = 기준가 대비 ±10% 변동, 동적 VI = 직전 체결가 대비 ±2~3% — mixing both let through a lot of noise-scale triggers (chart-verified pattern that day: buys landing right at the top of a 6~7% dynamic-VI spike, immediately stopped out on the reversion). `FID_MRKT_CLS_CODE` changed from `0`(전체) to `K`(거래소/코스피) the same day for the KOSPI-only restriction below. The VI event's `vi_kind_code`/`vi_dprt` are snapshotted onto `Order.viKindCode`/`viDprt` at buy time so the 정적-only filter (and any future threshold change) can be audited/compared directly from the DB. `MAX_VI_DPRT_PERCENT`(15%, added 2026-08-10) additionally excludes candidates whose `vi_dprt`(정적VI발동괴리율) is at or above this threshold — 정적 VI's price band is ±30% from the reference price, so a release this close to that band is effectively an upper-limit (상한가) catch with nowhere left to go but down; confirmed the same day with the very first batch of live trades under the 정적-only filter: the two releases with `vi_dprt` 29.95%/16.38% both stopped out, while every normal ~10%-band release (the vast majority, since that's the static-VI trigger threshold itself) had mixed/positive outcomes.
- `gap-scanner.ts` — opening gap-up: KIS `ranking/fluctuation` doesn't expose 시가 directly, so it's derived from `prdy_ctrt` (vs prev close) and `oprc_vrss_prpr_rate` (vs today's open) returned on the same row; only runs for `gapScanWindowMinutes` after session open, then self-stops (`gapStrategyEnabled`). **Disabled** (`gapStrategyEnabled=false`) since the 2026-08-07 KOSPI-only experiment started: unlike `volume-rank`/`inquire-vi-status`, KIS's official `fluctuation.py` example only documents `fid_cond_mrkt_div_code` as accepting `J`/`W`/`Q` (not the `K` used elsewhere) without saying which of those actually scopes to KOSPI-only, so the code wasn't changed here to avoid silently guessing wrong on a param that places live orders — needs live verification (or a client-side market-code filter, same technique as `search-stock-info` below) before re-enabling.

**Market regime filter** (`trading/market-condition.ts`): a 1-minute-interval KOSPI index cache (`fetchIndexPrice`, `kis/quotations.ts`) that all three scanners above check at the top of every tick — if it says "중단", the tick returns immediately without calling KIS at all (exit/sell logic is unaffected, this only gates new entries). All three are long-only momentum strategies betting on the same direction, so a KOSPI downturn drags all three down together with zero diversification benefit (2026-08-06: `vi_release`/`gap_up` both took large losses on a down day). Redesigned 2026-08-07 from a previous-close-relative sign check (`bstp_nmix_prdy_ctrt > 0`) to a **tick-to-tick instantaneous rate of change**: `Δ = (현재 틱 지수 - 직전 틱 지수) / 직전 틱 지수 × 100`, allow/resume when `Δ ≥ +0.02%`, stop when below that — with a `CONFIRM_TICKS`-consecutive-tick confirmation before actually flipping state, so a single noisy tick can't toggle it. The previous-close version was replaced because it can't tell an early-morning rally that fades all day (KOSPI nominally positive most of the morning while individual positions were already bleeding) from an actual sustained uptrend — verified by walking that day's stopped-out codes through KIS's intraday minute chart (`inquire-time-itemchartprice`) and finding the drawdowns lined up with the KOSPI/KOSDAQ curve, not with isolated reversals. Fails safe on a lookup error (keeps the previous state rather than flip) for the same single-point-of-failure reason as `fetchStartingCash` etc. Each confirmed stop/resume transition sends its own Discord message (🟡 스캔 중단 / 🟢 스캔 재개, via `sendDiscordMessage()` directly — not through `logTradeEvent()`/`trade_events`, since this is an operational state change rather than a trade event tied to a session). The latest computed tick delta is exposed via `getMarketTickDelta()` and snapshotted onto `Order.kospiDeltaAtBuy` (in `execute-buy.ts`) and `PositionWatcher.kospiDeltaAtSell` (in `watchForSell()`'s sell branch and `forceSell()`) purely for later review — not read anywhere as a trading condition beyond the bullish/bearish gate itself. `CONFIRM_TICKS` was `2` at first-deploy (2026-08-07) but bumped to `4` on 2026-08-10 after the first live trading day flipped state **41 times** (some transitions only 2 minutes apart) — too noisy to be a meaningful gate at that setting. The initial/session-reset value of `bullish` was also flipped from `true` to `false` the same day (both the module-level initializer and `stopMarketConditionCache()`'s reset): starting/resetting to "허용" meant every session opened with scanning immediately unblocked before the filter had measured anything at all — the exact "아직 방향이 안 잡힌 구간을 그대로 통과시키는" gap the filter exists to close. Starting from `false` means each session (and each restart) needs `CONFIRM_TICKS` consecutive up-ticks to actually observe a confirmed rising trend before scanning opens, at the cost of skipping whatever happens in the first few minutes after 09:00.

**KOSPI-only universe restriction** (2026-08-07, experiment — `viActedCodes`/`passedCodes` unaffected, this only changes what KIS returns as candidates): since the market regime filter above measures the KOSPI index specifically, buy targets were narrowed to KOSPI-listed stocks too, to keep the signal and the universe consistent while this is evaluated (KOSDAQ may be added back later). `scanner.ts`/`vi-scanner.ts` do this via documented KIS market-scope params (see bullets above); `gap-scanner.ts` is disabled instead of guessing at an unverified param (see above). Market classification for an arbitrary code (if ever needed again, e.g. to audit what actually came through) goes through `search-stock-info` (`scts_mket_lstg_dt` present → KOSPI, `kosdaq_mket_lstg_dt` present → KOSDAQ) — real-credentials-only, same `EGW02006` restriction as `chk-holiday`.
- Each scanner keeps its own same-day dedup pool (`passedCodes` / `viActedCodes` / `gapPassedCodes` on `trading_sessions`) but all three share one `getOrderedCodesToday()` check (`session-orders.ts`) so they never double-buy the same code. All three pools follow the same rule: every code seen in a tick's candidate list gets marked "passed" regardless of whether `executeBuy()` actually bought it — a skip (insufficient cash, KIS rejection, etc.) is *not* retried later that day, by design. `gap-scanner.ts` didn't have this pool until 2026-08-04 (it only excluded codes actually bought via `getOrderedCodesToday()`), so a skipped candidate got re-considered on every 5-second tick for the rest of the scan window instead of being left alone like the other two strategies. **Known gotcha, fixed 2026-08-10**: `getOrderedCodesToday()` alone can't stop two *different* strategies from buying the same code in the same instant — it's a DB read, so if two scanners' ticks both read it before either has committed its `Order` row, both see the code as unordered and both buy (2026-08-10 incident: `volume_rank`/`vi_release` bought `217590` 0.9s apart; KIS merged them into one 129-share holding, one `PositionWatcher` sold the whole thing, the other's own sell attempt then failed with "no balance" and it was left stuck in `error`). `execute-buy.ts` now holds a module-level in-memory `Set` (`buyLocks`) as a same-process mutex: `executeBuy()` — the one shared entry point all three scanners funnel through — synchronously reserves the code as its very first statement, before any `await`, and releases it in a `finally` regardless of outcome. This works because JS is single-threaded and nothing can interleave between two synchronous statements, so whichever call reaches that line first wins; no DB round-trip, no persistence needed (a restart mid-attempt just drops the lock, which is fine — the lock only needs to survive the few seconds one buy attempt takes).

**Position sizing** (`execute-buy.ts`, revised 2026-08-04): per-trade amount is `min(availableCash, maxOrderAmt)` where `maxOrderAmt = min(startingCash * orderAmtPercent / 100, TradingConfig.maxOrderAmt)`. `startingCash` (`TradingSession.startingCash`) is a **one-time snapshot** of `prvs_rcdl_excc_amt` (가수도정산금액: cash net of what's already tied up in open positions; `dnca_tot_amt`/예수금총금액 looked like the obvious field but stays fixed regardless of current holdings, confirmed by a live paper-account call — don't use it) taken once at session open and never recalculated during the day. The same-day first version of this instead recalculated `orderAmtPercent` against the *current* `availableCash` on every buy — which meant order size shrank every time a new position opened (less cash left → smaller %), feeding a runaway loop of smaller and smaller orders and an ever-growing open-position count; combined with the pagination gotcha above, this is what produced the 134-stray-positions state. Anchoring the % to a fixed `startingCash` snapshot instead keeps order size constant all day regardless of how many positions are currently open. A `minOrderAmtPercent` floor (also against `startingCash`, default 5%) was added at the same time: once *current* `availableCash` drops below it, `executeBuy()` skips the candidate outright even if the scanner found one — this is the mechanism that caps how many concurrent positions can be open, instead of an explicit max-position-count setting. `TradingConfig.maxOrderAmt` (default ₩1,000,000) remains a pure safety ceiling on top of the % calculation, not the order amount itself. Candidate-price filtering in `scanner.ts`/`gap-scanner.ts` uses a separate `maxCandidatePrice` field, unrelated to order sizing. `prvs_rcdl_excc_amt` is confirmed present on the **paper** `inquire-balance` response; not yet verified on **real**'s `inquire-balance-rlz-pl` — check before switching `KIS_ENV`.

**Exit** (`src/trading/position-watcher.ts`): per-position state machine (`checking → watching_for_sell → sell_waiting → done|error`), one row per `Order` in `position_watchers`. Take-profit (`sellAmtHigh`) is fixed at entry; stop-loss (`sellAmtLow`) trails a tracked high-water mark (`peakPrice`) upward as price rises and never retreats. Reacts to `BalancePoller` (`balance-poller.ts`, the server-side `CheckBalance` equivalent — one 1s poll loop for the whole process, active only while it has listeners). A third exit path, **profit timeout** (`PROFIT_TIMEOUT_MS`, added 2026-08-10), sells at the current price once a position has been at/above its real entry price (`entryPrice`, from KIS `pchs_avg_pric`) for that long without reaching the take-profit line — added after a live case (`029460`, 2026-08-10) showed a VI-release buy peaking at +2% just 4~5 minutes in, then bleeding back out over ~30 minutes into a small trailing-stop loss instead: the underlying bet is that a VI-momentum entry which can't clear the take-profit target within a few minutes has already lost its buying pressure and is more likely to reverse than to break out, so locking in whatever gain (or breakeven) exists beats waiting on the trailing stop. `profitSince` (the timestamp of first crossing `entryPrice`) is set once and, deliberately, never reset even if price dips back down afterward — the assumption is evaluated once, not re-armed on every wiggle. The timeout only fires while price is still `>= entryPrice` at check time; if price has already fallen below entry, that's the trailing stop-loss's job, not this path's. `entryPrice` itself isn't a separate persisted column — it's derived from the already-persisted `sellAmtHigh`/`highPercentage` on `resume()` (`entryPrice = sellAmtHigh / (1 + highPercentage/100)`), so a restart doesn't lose it. This exit records as `highOrLow: 'timeout'` (alongside the existing `'high'`/`'low'`) so it's distinguishable from the other two paths in later analysis. Started at `5` minutes, bumped to **`10`** the same day before ever deploying: back-tested against that day's own KIS minute-chart data, `5` would have cut 2 of the day's 4 actual winners (`002420`, `071320`) down from a full +3% to roughly +0.1~0.3% — both stalled near entry around the 5-minute mark and only broke out 20~50 minutes later. `10` doesn't fully fix this (`071320` was still flat at the 10-minute mark that day) but is directionally better with the same 12-trade sample; a further win-rate-focused pass (e.g. filtering entries by news/catalyst) was deferred rather than continuing to hand-tune this constant on a small sample.

**Persistence**: Postgres via Prisma (`prisma/schema.prisma`, migrations in `prisma/migrations/`). `TradingConfig` is a singleton row (id=1) holding everything the AdvanceOrder screen used to control, plus per-strategy on/off + threshold fields (`kisEnv` was a dead column here until removed 2026-08-05 — nothing ever read it; the *actual* real/paper switch is the `KIS_ENV` env var, see KIS client above and Deployment below). `Order`.`sourceStrategy` tags which scanner bought a position (`'volume_rank' | 'vi_release' | 'gap_up'`). `Order` also carries a few buy-time-only snapshot columns purely for later review (added 2026-08-07, never read as trading conditions): `viKindCode`/`viDprt` (vi_release only, from `ViStatusItem`) and `kospiDeltaAtBuy` (from `market-condition.ts`'s `getMarketTickDelta()`, see the Market regime filter note above) — `PositionWatcher.kospiDeltaAtSell` is the matching sell-time snapshot, written alongside `sellPrice`/`sellQty`/`pnl`. `TradeEvent` is the append-only log (buy/sell/error/session boundaries) — but as of 2026-08-05, `TradeEvent.payload` is no longer the source of truth for a trade's outcome: `PositionWatcher` has its own `sellPrice`/`sellQty`/`pnl`/`closedAt` columns, written directly at the moment a sell order is confirmed (in `watchForSell()`, `forceSell()`, and `liquidateStalePositions()`) rather than reconstructed later by matching `TradeEvent` rows back to `Order` by stock code — see the Notifications section below for why that reconstruction was fragile.

**Notifications** (`src/notify/discord.ts` + `src/trading/log-trade-event.ts`): `logTradeEvent()` is the *only* place code should write to `trade_events` — it wraps the Prisma insert and, for `session_start`/`session_end`/`buy_executed`/`sell_executed`/`forced_liquidation`/`sell_failed`/`error`, also sends a color-coded embed to `DISCORD_WEBHOOK_URL` (no-ops silently if that env var is unset — a notification failure must never block trading). The embed description includes the stock name next to the code (`[name(code)]`) via an optional `name` on `LogTradeEventInput` — formatting-only, stripped before the Prisma write since `TradeEvent` has no `name` column (`Order.name` is the source of truth). `sell_executed`'s message also includes realized P&L, computed from the live KIS `pchs_avg_pric` at sell time (not `Order.buyPrice`, which is only the entry-strategy's reference price and can diverge from the actual market-order fill — see the VI-momentum note above). `buy_failed` is still recorded but not notified — it includes routine rejections (e.g. 매매불가 종목) common enough that alerting on every one isn't useful yet. An optional `notify: false` on `LogTradeEventInput` (default `true`) writes the DB row without sending the Discord embed even for a normally-notified type — added 2026-08-04 for `liquidateStalePositions()` (see Cron schedule above), which would otherwise send one `forced_liquidation` message per stale code (134 on the day this was found) instead of one "전일 잔여 포지션 정리 N건 완료" summary; extended 2026-08-05 to `liquidateTodaySession()`'s 15:15 sweep too (`PositionWatcher.forceSell()` now takes an `options.notify` param, default `true` so the admin single-position force-sell button in `trading-control` still gets its own immediate notification) — the bulk EOD sweep passes `notify: false` per position and sends one "15:15 장마감 강제청산 완료" summary afterward instead of one message per liquidated code. `closeTodaySession()` (`cron/session.ts`) additionally builds a same-day summary (`buildSessionSummary`, doubling as the daily report) — buy count / done vs still-open sell count / estimated realized P&L, **capital utilization** (today's total invested amount vs `TradingSession.startingCash`, a `prvs_rcdl_excc_amt`-based snapshot taken once at `openTodaySession()` — null and silently skipped for sessions opened before this field existed), and **per-strategy win rate / avg win-loss %** — and includes it all in the session_end message. As of 2026-08-05 this reads `PositionWatcher.sellPrice`/`sellQty`/`pnl` directly (see Persistence above) rather than joining `TradeEvent` back to `Order` by stock code; the old approach silently undercounted real P&L whenever a sell path didn't populate `payload.pnl` (see the forceSell gotcha just below) — found by comparing a day's real account P&L (+30만원대) against what the Discord report showed (7,854원), off by exactly the sum of that day's forced-liquidation trades. **Known gotcha**: `PositionWatcher` needs to pass `sessionId` into every `logTradeEvent()` call itself (it snapshots `sessionId`/`name` at construction, same pattern as the entry-percentage snapshot) — until 2026-08-03 it didn't, so every `sell_executed`/`error`/`forced_liquidation` event was written with `sessionId = NULL` and silently excluded from `buildSessionSummary`'s per-session query (buy-side events were unaffected — `execute-buy.ts` always passed it correctly). Any new call site that logs an event tied to a specific position must go through `PositionWatcher`'s own `sessionId`, not assume it's optional. **Fixed 2026-08-05** (previously "known gap, not yet fixed"): `PositionWatcher.forceSell()`'s `logTradeEvent()` call used to log only `payload: { qty }` — unlike the normal sell path in `watchForSell()`, it never captured `price`/`pnl`, so every forced-liquidation sell (the 15:15 EOD sweep, and `liquidateStalePositions()`'s 09:00 cleanup) was invisible to realized-P&L/per-strategy stats even though real money moved. Now `forceSell()` computes `price`/`pnl` off `current.prpr`/`pchs_avg_pric` the same way `watchForSell()` does and persists them onto `PositionWatcher` immediately (before the sell is even confirmed filled — durable across a restart, not just carried in memory) rather than waiting for the `done()` transition.

**Logging**: `lib/logger.ts`'s `installTimestampedConsole()` (called once, right after the import block in `main.ts`) monkey-patches `console.log`/`warn`/`error` so every call is prefixed with a KST timestamp via `lib/date.ts`'s `nowKstTimestamp()` — added 2026-08-04 after finding the deployed container's `docker logs` output had no time information at all, making it impossible to reconstruct an incident timeline after the fact. Patched once at the entry point rather than touching each of the many call sites individually.

**REST API** (`src/http/`, mounted at `/api`): every route requires an `x-api-key` header matching `API_TOKEN` — **fail-closed**, i.e. if `API_TOKEN` isn't set the whole API 500s rather than opening up. `GET /status`, `GET/PUT /config`, `GET /positions` + `POST /positions/:code/force-sell`, `GET /orders`, `GET /events`, `POST/DELETE /devices` (FCM token registry — registration only, nothing actually sends an FCM push yet; live trade/session alerts go out via the Discord webhook above instead).

## Control frontend (apps/trading-control)

React 18 SPA (Vite, styled-components) — a REST client for `apps/trading-server`'s `/api/*`, nothing else; it does not talk to KIS directly. Meant to be loaded inside an Android WebView (native shell/bridge is a separate project, out of this repo's scope).

- `src/api/client.ts` — thin `fetch` wrapper that attaches `x-api-key: VITE_TRADING_SERVER_API_TOKEN` to every call against `VITE_TRADING_SERVER_HOST`.
- Pages (`src/app/pages/`): `DashboardPage` (status + positions, 5s poll, force-sell button), `ConfigPage` (GET/PUT the `TradingConfig` row via an `@mint-ui/core` `Table` form, including `formType: 'check'` for the boolean strategy toggles), `LogsPage` (`trade_events`, 5s poll).
- Reuses `@mint-ui/core` (the same third-party component kit `services/trading` uses) plus only the *generic* pieces of `shared/ui/design-system-v1` — `GlobalStyleV1`, `MainToastContextProvider`/`useShowToastHook`, `ComponentRoutes`/`ComponentRoute`/`ComponentRouteLink`. Deliberately does **not** reuse `AppContainer`/`PageContainer`/`Header`/`Footer`: `Footer` hardcodes the legacy app's own menu items and `PageContainer` is wired to Recoil's `PageState`, so `trading-control` has its own minimal shell (`app.tsx`) instead and carries no Recoil dependency at all.
- Two bugs found and fixed here that affect any future consumer of these shared libs: `shared/ui/design-system-v1`'s `routes/index.ts` barrel was missing `export * from './ComponentRouteLink'` (legacy code worked around it with a relative import instead of the alias). `@mint-ui/core`'s `Flex` defaults to `height: 100%; overflow: auto;` when `flexHeight`/`flexOverflow` aren't passed, which clips column-stacked content with more than ~2 rows — worth remembering when composing new layouts with it (`trading-control`'s local `Card` component sets `flexHeight='fit-content'` to opt out).

## Deployment (Jenkins on the home server)

`apps/trading-server` deploys via a shared Jenkins instance at `home.ribs.kr:10000` (also hosts an unrelated project, "ribs" — its jobs were the template for these). Not part of this repo, but documenting the conventions here since the job definitions are the actual source of truth for how this app runs in production:

- **Jobs**: `build-trading-server` (checks out the `feature/2026-new-bot` branch → `npm ci` + `npm run db:generate` + `npm run build-trading-server` + `npm run image-trading-server`, i.e. `docker build -t trading-server:latest`) → on SUCCESS auto-triggers `deploy-trading-server` (`docker rm -f trading-server` then `docker run` with secrets injected as `-e VAR=$VAR`, `-p 3364:3364`) → `stop-trading-server` (`docker stop trading-server` — the fast kill-switch if something looks wrong; posts to Discord either way).
- **Credentials**: every secret `.env.local` value trading-server needs is duplicated into Jenkins as a Secret-text credential prefixed `TRADING_` (e.g. `TRADING_DATABASE_URL`, `TRADING_KIS_PAPER_APP_KEY`, `TRADING_DISCORD_WEBHOOK_URL`), bound in `deploy-trading-server`'s `SecretBuildWrapper`. Non-secret values (`KIS_REAL_HOST`/`KIS_PAPER_HOST`/`HOST`/`PORT`, and **`KIS_ENV=paper`**) are hardcoded directly in the job's shell command instead of round-tripped through a credential — `KIS_ENV` in particular is deliberately not a credential so it can't be silently left on `real`.
- **Known gotcha**: `POST /job/<name>/config.xml` (in-place job update via the Jenkins REST API) 500s under this instance's permission setup, even though `createItem`/`doDelete`/credential management all work fine with the same token. The working pattern is delete-then-`createItem` instead (fine here — these jobs carry no build history worth preserving).
- **Known gotcha**: the Dockerfile's `prisma generate` step must pin the same Prisma version as `package.json`'s `"prisma"` devDependency (currently `6.19.3`). An unpinned `npx prisma generate` grabs whatever's newest on the registry at image-build time — Prisma 7 dropped the `datasource.url`-in-schema syntax this project's `schema.prisma` uses, so an unpinned build breaks (this happened on the very first real deploy).
- **Port**: 3364 (container and host). 3363 was tried first but the home network's port-forwarding was already pointed at the unrelated "ribs"/sisulbot service.

## Commands

Run everything from the repo root via `nx` (or `npx nx` if not installed globally); project names come from each `project.json` (`stock-trading-bot`, `kis-server`, `trading-server`, `trading-control`, `trading`, `kis`, `api-hook`, `util-hook`, `global`, `design-system-v1`, `date`, `localstorage`).

```bash
# Frontend app (dev server, port 4200)
npm start                          # = nx serve stock-trading-bot
npm run build                      # = nx build stock-trading-bot, then after.mjs copies dist into an Android assets folder (path hardcoded — irrelevant off that machine)

# Proxy server (dev, defaults to port 3000) — legacy, used only by apps/stock-trading-bot
npm run server                     # = nx serve kis-server
npm run build-server               # = nx build kis-server
npm run image-server               # docker build using apps/kis-server/Dockerfile
nx docker-build kis-server         # alternative docker build target defined in project.json

# Trading server (dev, defaults to port 3001)
npm run server-trading              # = nx serve trading-server
npm run build-trading-server        # = nx build trading-server
npm run image-trading-server        # docker build using apps/trading-server/Dockerfile
npm run db:generate                 # prisma generate (schema: apps/trading-server/prisma/schema.prisma)
npm run db:migrate                  # prisma migrate dev — needs DATABASE_URL in .env.local
npm run db:deploy                   # prisma migrate deploy (non-interactive, for CI/deploy)

# Control frontend (dev server, port 4201)
npm run start-control                # = nx serve trading-control
npm run build-control                # = nx build trading-control

# Lint (per-project; also runs via nx affected)
npx eslint --fix .                 # = npm run fix
nx lint <project>
nx affected -t lint --base=main    # see affected.defaultBase gotcha in the Tests notes below

# Tests
nx test trading                    # services/trading — Jest
nx test <shared-lib-name>          # shared libs (kis, api-hook, util-hook, global, design-system-v1, date, localstorage) — Jest
nx test stock-trading-bot          # apps/stock-trading-bot — Vitest
nx test <project> --testFile=<pattern>   # single test file (Vitest projects)
nx affected -t test --base=main    # run tests for everything touched vs main
```

Notes:
- Both React apps (`stock-trading-bot`, `trading-control`) use **Vitest** (`@nx/vite:test`); `services/trading` and every `shared/*` library use **Jest** (`@nx/jest:jest`) — check `project.json`'s `test` target before assuming which runner applies. `trading-server` and `trading-control` have test targets wired up (Jest and Vitest respectively) but no test files exist yet in either.
- `nx.json`'s `affected.defaultBase` is stale (`"master"`, a branch that doesn't exist in this repo — the real default branch is `main`), so plain `nx affected ...` fails with a git revision error; always pass `--base=main` (or `--base=origin/main`) explicitly.
- Nx caches `build`/`lint`/test targets; if output looks stale, add `--skip-nx-cache`.
- `.env.local` (git-ignored, shared by both Vite apps and `trading-server`'s `dotenv.config()`) holds all secrets/config; **`.env.example` at the repo root is the checked-in, secret-free spec** — every var name, what it's for, its expected format, and where to obtain it (KIS appkey/secret/CANO come from the KIS developer portal — real and paper are separate applications with separate keys). New machine setup: `cp .env.example .env.local` then fill in real values. Never commit real values or print them.
- `JENKINS_API_TOKEN` also lives in `.env.local` (paired with the `goju2k` Jenkins user for Basic Auth) but isn't in `.env.example` — it's only used to script Jenkins job/credential setup from this machine (see Deployment below), no app code reads it.

## Conventions

- ESLint config (`.eslintrc.json`) extends `airbnb`/`airbnb/hooks`; notable non-default rules: single-quote JSX (`jsx-quotes: prefer-single`), always-multiline trailing commas, 2-space indent, no final newline (`eol-last: never`), enforced `import/order` (external → builtin → internal → sibling → parent → index, alphabetized, blank line between groups), `no-unused-vars`/`no-shadow` handled by the TS-aware variants only.
- Styling is styled-components throughout (Nx generator default is set to `"style": "styled-components"` in `nx.json`); new components/libraries generated with `nx g @nx/react:component|library` will inherit this.
- Korean-language inline comments and UI strings are used throughout the trading logic to describe domain behavior (state meanings, order semantics) — match this when touching those files.
- When adding/changing a KIS endpoint call in `apps/trading-server/src/kis/`, verify the exact `tr_id`/path/param names against KIS's own example code (`gh api repos/koreainvestment/open-trading-api/contents/examples_llm/domestic_stock/<endpoint>/<endpoint>.py`) rather than guessing — KIS's docs and field-naming aren't fully consistent across endpoints (e.g. `mksc_shrn_iscd` vs `stck_shrn_iscd` for "종목코드" depending on which ranking API). This is how every tr_id currently in the codebase was confirmed.
